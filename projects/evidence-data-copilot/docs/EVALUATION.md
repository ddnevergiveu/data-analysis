# 可手算评估集

评估目标是验证 **SQL 执行、离线规则规划、已知不支持查询的拒绝行为**。本评估不请求任何 LLM，不衡量模型自然语言准确率，也不声称覆盖任意 SQL 或全部安全风险。

## 固定输入

每次评估都在临时目录新建数据库，使用下面六笔合成订单。金额为每笔订单金额，保留两位小数；没有真实客户数据。

| order_id | customer_id | order_date | region | amount |
| --- | --- | --- | --- | ---: |
| o1 | A | 2026-01-02 | east | 100.00 |
| o2 | B | 2026-01-03 | north | 50.00 |
| o3 | A | 2026-02-02 | east | 200.00 |
| o4 | C | 2026-02-03 | west | 80.00 |
| o5 | B | 2026-02-04 | north | 50.00 |
| o6 | D | 2026-02-05 | east | 20.00 |

## 独立预期值

这些结果直接从表格手算，写在评估集里；不会先调用被测试程序再把其输出当成正确答案。

| 指标 | 手算 | 正确值 |
| --- | --- | --- |
| 订单数 | 六个不同 order_id | 6 |
| 客户数 | A、B、C、D | 4 |
| 总销售额 | 100 + 50 + 200 + 80 + 50 + 20 | 500.00 |
| 平均客单价 | 500 / 6 | 83.333333… |
| 月度销售额 | 1 月 100+50；2 月 200+80+50+20 | 1 月 150.00；2 月 350.00 |
| 地区销售额 | east 100+200+20；north 50+50；west 80 | 320.00、100.00、80.00 |
| 复购客户率 | A、B 有两单；C、D 各一单 | 2 / 4 = 0.5 |
| 客户消费排名 | A 300；B 100；C 80；D 20 | A、B、C、D |

数值比较允许浮点聚合的微小误差，Decimal 字符串仍按数值比较。SQL 执行组验证未舍入客单价 `500/6`；规则规划组按其公开口径验证保留两位小数的 `83.33`。规则输出还核验订单数等辅助列，按列名提取后对照独立预期。月份按 `YYYY-MM` 比较，避免 DATE 与 TIMESTAMP 序列化差异影响业务含义。排名 SQL 明确指定排序；不依赖数据库偶然返回的行顺序。

## 19 个检查分别测什么

| 组别 | 数量 | 覆盖 |
| --- | ---: | --- |
| query_execution | 6 | 订单/客户/总额、客单价、月份、地区、复购 CTE、消费排名 |
| rule_planning | 6 | 六个固定中文问题经过离线规则规划，执行所得 SQL，再核对手算结果 |
| query_rejection | 7 | 多语句、UPDATE、DELETE、外部文件读取、系统目录表、未知函数、表函数 |

规则问题为：“总销售额是多少？”、“平均客单价是多少？”、“每月销售额是多少？”、“各地区销售额排名”、“客户复购率是多少？”和“消费金额最高的前10位客户”。它们只验证这六个已支持模板，不代表对任意中文问题的理解能力。

报告字段包括 `total`、`passed`、`failed`、`all_passed`、`scope` 和逐项 `cases`。失败会保留预期、实际输出或异常类型，便于复核。拒绝检查要求明确抛出 `ValueError`，其他崩溃不算通过。

可通过 CLI 的 `evaluate` 子命令执行并保存结果。也可在项目目录运行：

```bash
python -m unittest discover -s tests -p test_evaluation.py -v
```

测试还故意将查询引擎替换为始终返回 999 的错误实现，确认评估不会把错误答案或没有拒绝的查询算作成功。

## 解释边界

19/19 只表示这个固定合成回归集全部通过，不能据此声称 LLM 准确率 100%、真实业务分析准确率 100%，或程序已具备对任何不可信 SQL 的完整隔离。真实模型验证需要另外记录模型、版本、提示词、问题集、拒答、错误 SQL、数值结果和人工复核，并将测试题与开发样例分开。
